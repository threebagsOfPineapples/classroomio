# 钉钉员工批量同步可行性

## 2026-10-10 实施更新

已增加部门树读取、员工分页去重、预览与事务确认同步，后台入口为“组织 → 钉钉同步”。仅系统管理员可导入；新账号默认普通学员，已有权限及学习记录保留。部门新增外部身份字段，员工沿用 CorpId + userid 绑定；多部门员工需要选择主要部门，冲突账号需先处理或自行绑定。缺工号、企业邮箱允许保留空值；不会将钉钉登录当作邮箱验证，不会因一次读取缺失自动删除员工。

本次两个部门读取权限已由应用负责人开通，实际接口返回成功；一次全量只读读取获得 286 个部门、931 名员工，其中 18 人有多个部门。此读取结果不代表已经完成账号导入或真实扫码验收。以下保留 2026-09-28 的历史可行性调查。

日期：2026-09-28。范围：官方资料调查与本仓库实现核查；未修改钉钉配置、调用公司通讯录、导入员工或调整权限。

## 结论

可以通过钉钉通讯录接口批量读取工号、部门归属、岗位，并转换为培训员工档案。但这不是普通员工扫码后自然获得的能力，需要企业应用获得对应通讯录权限和数据范围；本系统目前只实现本人信息读取，尚未实现批量同步。

## 字段与限制

| 培训字段 | 钉钉字段 | 落地注意事项 |
| --- | --- | --- |
| 员工号 | `job_number` | 源档案必须已填写，不能将空值编造为工号 |
| 岗位 | `title` | 通讯录职位文本，不等同于一套岗位字典 |
| 部门 | `dept_id_list` | 是部门 ID 列表；需读取部门树映射名称和上下级 |
| 外部员工标识 | `userid` | 建议使用企业 CorpId + userid 标识来源，不按姓名自动合并 |

字段依据：[阿里官方钉钉部门用户完整信息 API](https://jaq-doc.alibaba.com/docs/api.htm?apiId=52238&source=search)。同步需要逐部门、分页读取；多部门员工必须去重。当前培训档案只有单个部门，需要确认主部门映射，不能直接取列表第一项当成主部门。这些是本项目接入设计判断。

## 需要管理员配合的部分

已有企业应用可先核查授权，不必默认新建。核心是部门信息读、部门成员读、成员信息读，并配置覆盖目标员工和相关部门的权限范围。手机号、邮箱属于额外资料需求，不应为了同步工号和岗位就盲目申请全部权限。普通员工无法自行扩大企业应用的授权范围。

阿里云官方同步说明明确列出上述三类基础权限、工号需预先填写及通讯录范围要求：[钉钉用户同步](https://help.aliyun.com/zh/qwenwork/enterprise-ultimate-users-user-sync-dingtalk)。应用创建与申请权限需要具备相应管理身份：[企业或应用管理员前提](https://help.aliyun.com/zh/agentidentity/configure-dingtalk-as-the-identity-provider-for-the-user-pool)。

## 是否需要登录回调

仅由服务器持应用凭据拉取通讯录，可以与扫码登录分开实施；该拉取流程不依赖员工逐个扫码，也不需要为读取任务增加网页登录回调。若同时启用网页扫码登录，则仍需相应登录回调；若以后做实时人员变更订阅，还需另外设计事件接收流程。这是根据应用令牌鉴权流程作出的实现判断：[企业内部应用 accessToken](https://open.dingtalk.com/document/orgapp/obtain-the-access_token-of-an-internal-app)。
